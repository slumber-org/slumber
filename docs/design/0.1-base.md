## Goal

- The immediate goal is to define the smallest coherent and extensible foundation for SLUMBER.
- Consistency across the project was identified as a key design principle, particularly for configuration schemas and definitions of UI components, processing units, and other extensible components.

## Terms

| Term | Meaning |
| --- | --- |
| Study | Researcher-authored package on disk: `study.yaml`, condition files, assets, and run output. |
| Condition | One protocol arm of a study (e.g. active vs control). |
| Activity | One participant-facing step (e.g. instruction, sleep). |
| ActivityHost | API injected at `mount`: UI container, `complete()`, `emit()`, path helpers. Provided by the layout/UI runtime; not part of `Activity`. |
| Phase | Named stage of a condition (e.g. setup, sleep): a set of activities, shown in a layout. |
| Layout | How a phase's body is arranged inside the AppFrame. |
| UI | How a run is presented. Selected by `study.ui` (`gui` or `headless`). |
| AppFrame | GUI chrome (header and footer: logo, title). Study `ui.settings.frame` is the default; a phase may override (e.g. show/hide). |
| Pipeline | Named processing graph. |
| Unit | One ezmsg node in a pipeline. |
| Run | One execution of a condition. |
| RunEngine | Runtime that drives a run. It maps events to actions until `end_run`. |
| Plugin | A concrete implementation bound to a `type` key (activity, unit, or built-in UI/layout). Discovered via entry points or a built-in map. |
| Extension | Optional installable package that contributes plugins (and maybe CLI), e.g. `slumber-somnio`. |

## Overview

A researcher authors a study package. A participant run executes a condition.

```
study.yaml + conditions/ + assets/
        ↓ load + validate plugins
   RunEngine
        ├── UI (gui: AppFrame + layout + activities)
        └── pipelines (start/stop subprocess)
        ↓
   runs/…/run.json + artifacts
```

## Design

### Plugins

```
YAML → schemas (shape only, no registry) → config (resolve_plugin_spec) → runtime
```

```python
class ConfiguredPlugin(ABC):
    """Shared settings_model contract for activities, layouts, UI adapters."""

    settings_model: ClassVar[type[BaseModel] | None] = None

class PluginSpec(BaseModel):
    """YAML reference to a typed implementation (UI, layout, activity, or unit)."""

    type: str                                                 # Entry-point name or built-in key.
    settings: dict[str, Any] = Field(default_factory=dict)    # Optional dict validated by that implementation's settings model.
```

- Core folder `plugins/` is discovery only (registry, errors, `ConfiguredPlugin`).
- Runtime ABCs: `Activity`, `Layout`, `UIBackend`. `ez.Unit` stays as-is; satisfies settings validation via `SETTINGS`.
- Built-in UI and layouts use the same `resolve_plugin_spec` path as entry-point plugins.

| Location | `type` examples | Group |
| --- | --- | --- |
| `study.ui` | `gui`, `headless` | built-in |
| `phase.layout` | `stepper`, `hub` | built-in |
| `phase.activities[]` | `instruction`, `sleep` | `slumber.activities` |
| `pipeline.units[]` | `clock`, `jsonl_writer` | `slumber.units` |

```toml
[project.entry-points."slumber.activities"]
instruction = "slumber.ui.activities.instruction:InstructionActivity"
sleep = "slumber.ui.activities.sleep:SleepActivity"

[project.entry-points."slumber.units"]
clock = "slumber.pipeline.units.clock:ClockUnit"
jsonl_writer = "slumber.pipeline.units.jsonl_writer:JsonlWriterUnit"
```

Extensions can also attach extra Typer apps through the `slumber.cli` entry-point group (not a PluginSpec).


#### Study manifest

```yaml

study_name: New Study

  type: gui
```

Optional overrides:

```yaml
conditions_dir: conditions
assets_dir: assets
runs:
  directory: runs
  layout: run-{run_id}
```

Minimal UI:

```yaml
ui:
  type: gui        # or headless
```

Full UI (all optional under `settings`):

```yaml
ui:
  type: gui
  settings:
    port: 8080
    favicon: "{assets_dir}/favicon.png"
    frame:
      header:
        logo: "{assets_dir}/logo.png"
        title: "{study_name}"
    layouts:
      stepper:
        previous_button: Previous
        next_button: Next
        complete_button: Complete
        show_activity_list: true
        allow_skip: false
```

Phase `layout.settings` merges over study `ui.settings.layouts.<type>`.

Phase optional `frame` merges over study `ui.settings.frame` (e.g. show/hide header or footer).

#### Condition YAML

Phases, pipelines, activities, and units are **lists with `id`**. Engine starts at `entry`. Actions refer to phase/pipeline ids; connections refer to unit ids.

```yaml
name: demo
entry: setup

phases:
  - id: setup
    title: Setup
    layout:
      type: stepper
      settings:
	      allow_skip: true
    activities:
      - id: welcome
        title: Welcome
        type: instruction
        settings: { content: "{assets_dir}/instructions/intro.md" }
    on:
      - event: phase_completed
        do:
          - start_pipeline: main
          - start_phase: sleep

  - id: sleep
    title: Sleep
    frame:
      header: false
      footer: false
    layout:
      type: hub
    activities:
      - id: sleep
        type: sleep
        settings:
          wake_button: "I'm Awake"
          end_button: "End Session"
        on:
          - event: marked_awake
            do: [{ start_phase: awakening }]
          - event: end_sleep
            do:
              - stop_pipeline: main
              - start_phase: morning

  - id: awakening
    title: Awakening
    layout:
      type: stepper
    activities:
      - id: awake
        title: You're awake
        type: instruction
        settings: { content: "{assets_dir}/instructions/awakening.md" }
    on:
      - event: phase_completed
        do: [{ start_phase: sleep }]

  - id: morning
    title: Morning
    layout:
      type: stepper
    activities:
      - id: complete
        title: Session complete
        type: instruction
        settings: { content: "{assets_dir}/instructions/morning.md" }
    on:
      - event: phase_completed
        do: [{ end_run }]

pipelines:
  - id: main
    units:
      - id: clock
        type: clock
        settings: { rate: 1.0 }
      - id: store
        type: jsonl_writer
        settings: { path: "{run_dir}/clock.jsonl" }
    connections:
      - [clock/OUTPUT, store/INPUT]
```

- PluginSpec is `type` + `settings` only. List instances (phases, pipelines, activities, units) have `id`; phases and activities may have `title` (defaults to `id`).
- Connection shorthand: `[OUTPUT, INPUT]`. Long form: `{ output: clock/OUTPUT, input: store/INPUT }`.

#### Path resolution

Relative paths resolve against the **study root**. Absolute paths are used as-is. Authors use placeholders when they need those locations.

| Placeholder | Expands to | Example |
| --- | --- | --- |
| `{assets_dir}` | study assets directory | `content: "{assets_dir}/intro.md"` |
| `{run_dir}` | this run's directory | `path: "{run_dir}/clock.jsonl"` |
| `{run_id}` | run id | layout / logging sinks |

```yaml
# → <study>/assets/intro.md
settings: { content: "{assets_dir}/intro.md" }

# → <run_dir>/clock.jsonl
settings: { path: "{run_dir}/clock.jsonl" }

# relative to study root (no placeholder)
settings: { content: assets/intro.md }

# absolute → unchanged
settings: { path: /tmp/clock.jsonl }
```

Placeholders expand first; then the result is resolved (relative → study root). Plugins receive the resolved path; they do not join against assets or the run directory themselves.

### UI

`study.ui` selects a UI backend. 0.1 backends are a built-in map, not an entry-point group. Both use the same RunEngine; they differ only in presentation.

| `type` | Role |
| --- | --- |
| `gui` | Participant window (NiceGUI): AppFrame + layout + activities. |
| `headless` | No window. Sequential activities auto-`complete()`. CI and demo without a browser. |

```
Run (ui.type: gui)
└── AppFrame                 ← study ui.settings.frame; phase.frame may override (show/hide)
      ├── header             ← logo, title (no help/menus/indicators in 0.1)
      ├── body               ← Layout mounts here
      └── footer             ← powered-by
```

One AppFrame for the run. Study frame is the default; on `start_phase`, apply that phase's optional `frame` override (e.g. hide chrome during sleep).

#### Layout

Each phase selects a layout. 0.1 layouts are a built-in map, not an entry-point group. The layout fills the AppFrame body and hosts that phase's activities.

| `type` | Role |
| --- | --- |
| `stepper` | Ordered activities: optional list + activity slot; nav buttons. |
| `hub` | One activity full bleed. |

Within a layout, only the activity slot remounts. On layout swap, the body remounts.

#### Activity contract

Activities are layout-agnostic. They call `host.complete()` / `host.emit(...)`; they do not define what completion means.

```python
class Activity(ConfiguredPlugin, ABC):

    @abstractmethod
    def mount(self, activity_host: ActivityHost) -> None: ...

    def unmount(self) -> None: ...
```

`ActivityHost` is injected at mount (container, `complete()`, `emit()`, path helpers). `complete` and `emit` are host services, not methods on `Activity`.

| Call | Audience | Meaning |
| --- | --- | --- |
| `complete()` | Layout | This mounted instance is finished as a step |
| `emit(name)` | RunEngine | A named study event happened |
| `phase_completed` | RunEngine (from layout) | Layout decided the phase is done |

```
Activity → host.complete() → Layout → (optional) phase_completed → RunEngine
Activity → host.emit(name)  → RunEngine
```

`complete()` is not `emit("complete")`: step lifecycle stays on the layout bus so every step finish does not hit condition `on:` handlers, and phase-level `complete` stays unambiguous. Open-ended activities (`sleep`) emit study events only and never complete; the phase leaves via `start_phase` / `end_run`, which unmounts them.

Every activity may call host methods; not every activity does. Sequential activities should `complete()` so a stepper can finish.

#### Branding and theme

| Concern | 0.1 decision |
| --- | --- |
| Palette | Fixed dark brand. Named tokens by role (page background, card surface, brand/nav, CTA/active, secondary/hover, attention/alert, body text). Align Quasar `ui.colors` with those tokens (CTA as Quasar `primary`; brand/nav colour used explicitly in chrome). |
| Typography | One typeface loaded once at GUI start. Shared type-scale tokens (`display`, `title`, `body`, `caption`) mapped to Quasar classes or CSS vars. |
| Logo / favicon | Package defaults under `ui/` assets. Study may override via `ui.settings.favicon` and `frame.header.logo` (paths relative to study root; typically `{assets_dir}/…`). |
| Shared chrome | Helpers: brand logo mark (size tokens: `hero` / `header` / `hub`), primary and outline CTA, surface card, confirm dialog. AppFrame header/footer and layout nav use the same helpers. |
| Docs | MkDocs CSS (`docs/stylesheets/extra.css`) mirrors the same palette tokens. |

```
ui/
  theme.py          ← tokens + Quasar colour map
  assets/
    logo.png
    favicon.png
  widgets/          ← logo mark, CTAs, surface card, confirm dialog
  …
```

```python
# Exact hex/names live in theme.py; call sites import tokens/helpers only.
PAGE_BG = "…"          # page background
SURFACE = "…"          # cards / panels
BRAND = "…"            # logo / nav
CTA = "…"              # primary buttons / active
SECONDARY = "…"        # secondary text / hover
ATTENTION = "…"        # alerts / high-contrast highlight
TEXT = "…"             # body text on dark

COLORS = {
    "primary": CTA,
    "secondary": SURFACE,
    "accent": ATTENTION,
    "dark": PAGE_BG,
    # …
}

LOGO_SIZE = {"hero": "…", "header": "…", "hub": "…"}
TYPE_SCALE = {"display": "…", "title": "…", "body": "…", "caption": "…"}
```

Apply once when the GUI backend starts (before AppFrame mount): load the typeface, set CSS variables from tokens, call `ui.colors(**COLORS)`, serve default logo/favicon (or study overrides when set).

```
GUI start
  → load typeface + CSS vars + ui.colors
  → resolve favicon (study setting or package default)
  → mount AppFrame (header logo: study setting or package default)
  → layout / activities use helpers + tokens only
```

Study branding is optional path overrides only:

```yaml
ui:
  type: gui
  settings:
    favicon: "{assets_dir}/favicon.png"   # omit → package default
    frame:
      header:
        logo: "{assets_dir}/logo.png"     # omit → package default
        title: "{study_name}"
```

### RunEngine

1. `load_study` + condition; resolve directory paths; `validate_study_plugins` (also on `study run`).
2. Create run directory, `run.json`, run logging (loguru from `study.logging`).
3. Resolve `study.ui` → GUI or headless.
4. Start engine; when GUI: apply theme (typeface / CSS vars / colours), mount AppFrame once (study frame defaults).
5. `start_phase(entry)` → apply phase `frame` override if any; layout + activities.
6. Event loop until `end_run` (stop pipelines, finalize).

| Module | Responsibility |

| `config/` | Load I/O: `load_study`, `validate_study_plugins`, `resolve_plugin_spec`, `resolve_settings`. |
| `plugins/` | Registry: `PluginRegistry`, `EntryPointGroup`, `ConfiguredPlugin`, errors. No activity/unit implementations. |
| `run/` | `RunEngine`, `RunContext`, run directory, run logging. |
| `pipeline/` | Pipeline manager (start/stop) and core units (`clock`, `jsonl_writer`). |
| `ui/` | AppFrame, GUI/headless adapters, layouts, activities, theme tokens, shared widgets, default logo/favicon. |
| `cli/` | Core commands (`study`, `doctor`); loads extra Typer apps from `slumber.cli`. |

## Scope

### In 0.1

**CLI (core):** `study init` / `validate` / `run --condition`. Local only.

**Actions:** `start_phase`, `start_pipeline`, `stop_pipeline`, `end_run`.
**Events:** `phase_completed` (from layout); activity `emit(...)` (e.g. `marked_awake`, `end_sleep`). No pipeline → engine events.

**Activities:**

| Key | Role |
| --- | --- |
| `instruction` | Markdown/text. Calls `complete()` on mount. |
| `sleep` | Wake / end buttons → `emit("marked_awake")` / `emit("end_sleep")`. Does not `complete()`. |

**Units** (for tests and the demo, not devices):

| Key | Role |
| --- | --- |
| `clock` | Periodic dummy samples |
| `jsonl_writer` | Append messages under the run directory |

**Demo study** (`examples/demo/`): instruction + sleep + clock → jsonl_writer. GUI and headless both use this package.

**Supabase:** out of core. Extract to `extensions/slumber-supabase`; attach CLI via `slumber.cli`. Local run must work without it.

**Logging:** run loguru handlers in 0.1. Audit / structured study events later.

**Paths:** relative → study root; no role-based bases; placeholders (`{assets_dir}`, `{run_dir}`, …); absolute accepted.

**Branding:** Fixed dark theme tokens + one typeface at GUI start; packaged default logo/favicon; shared chrome helpers; docs CSS mirrors the palette. Study may override logo/favicon paths only (via frame / favicon settings). No per-study palette or font YAML.

### Out of scope

- Complete theme system and runtime theme switching (light/dark product themes, per-study palettes, hot-swap)
- Custom icon library / full design-system guidelines beyond tokens and shared helpers
- Activities: survey, etc.
- Units: ZMax, audio, scoring, HDF5
- Event / audit logging: Structured study events
- Pipeline ↔ engine
- Required vs optional extensions: Study declares `requires: [somnio]`; doctor/install checks
- Supabase extension: Session scheduling, auth, condition sync
- UI extras: Custom layouts via entry points, indicators, menus
- Config sharing between conditions and study configs
- Stimulation: Cueing / stimulus delivery during sleep
- Multiple pipelines
